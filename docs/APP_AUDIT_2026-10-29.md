## 1. Baseline summary (10-29)

The map shell renders quickly (LCP 208 ms, CLS 0.005), though those figures do not include the slower data requests below. The sheet's scrolling area no longer collapses at 1024×768 (217 px) and there is no horizontal overflow at any tested size. The close button is never covered, and tiles answer in 2.5 ms. The failures this round are mostly **availability and trust**:

1. **Sign-in is a 500.** `/auth/login`, `/auth/register`, `/profile` and `/settings` all fail with a Starlette debug traceback that prints absolute server paths (H1).
2. **Backing services flap.** The municipality enrichment endpoint answered 503 on 6 of 6 direct calls, while `/ready` reports "ready". When it fails, the sheet loses its zone, hazard and risk values. The first municipality search and the sales feed also return 503 (H2).
3. **An arbitrary OMI quote is shown as the parcel's value.** The sheet says "The OMI zone was not detected automatically: check the selection", yet the headline shows 2,500–5,000 €/m² and a 9.6 % yield, taken from the first row of a 77-row list (zone B2, shops) (H3).
4. **Selection state is fragile.** The desktop sheet covers a parcel selected on the right of the map, the language switch discards the view and the selection, and a stale search dropdown survives a map click.

## 3. Findings

### High

#### H1. Sign-in, register, profile and settings return 500 with a debug traceback
- `GET /auth/login` and `/auth/register` return **500**. `/profile` and `/settings` redirect to the login page and end on the same 500. The header "Sign In" button, the sidebar's Profile and Settings, and the shortlist prompt all lead there. See `17-auth-login-500.png`.
- Cause (from the page): `TemplateNotFound: 'auth/login_base.html'`. The override [land_registry/templates/theme_overrides/auth/login.html:14](../land_registry/templates/theme_overrides/auth/login.html#L14) extends `auth/login_base.html`. The `aecs4u-theme` installed in this repo's `.venv` is **1.6.2**, which ships only `auth/login.html`; newer theme environments on this machine (for example `aecs4u-website` and `opendata`) have `login_base.html`. This is a theme-version/template-contract mismatch: the override expects a base template absent from the locked package.
- The response is the **Starlette debugger page** (`debug=app_settings.debug`, [main.py:448](../land_registry/main.py#L448)). It prints the full traceback, source lines and absolute paths such as `/mnt/mobile/git/aecs4u.it/land-registry/.venv/…`. If `debug` can ever be true in a deployed environment, this is an information leak.
- **Fix:** update the lock to a theme revision that ships `auth/login_base.html`, or change the override to use the installed theme's supported template API; then sync the environment. Add a smoke test that `GET /auth/login` returns 200. Make sure `debug` cannot be true in production config. Consider a friendly fallback so a missing theme template shows an error page, not a traceback.

#### H2. Backing services flap and `/ready` does not see it
- `GET /api/v1/enrichment/municipality/L781` returned **503** on 6 of 6 direct calls (`Municipality reference store temporarily unavailable`, in 3–5 ms). Earlier in the same session the browser got 200 for the same call. `GET /ready` returned `{"status":"ready","layers_available":19,…}` throughout.
- When it fails the sheet shows a banner ("Municipality data is temporarily unavailable. Zone, hazard and risk values may be missing.") with a Retry button, and the stat strip shows "—" for **Sale price, Flood and Risk**. The same parcel therefore shows a different headline depending on which request won (`07-parcel-sheet-loaded.png` versus `15-dark-desktop-sheet.png` and `14-phone-390.png`). The degradation itself is handled well.
- `GET /api/v1/map/search?query=Verona` returned **503** after 3.0 s on the first (cold) call, then 200 after 2.7 s, then 0.1 s for the same query. In the UI the first attempt shows "Search service unavailable; try again." and logs a console error. Pressing Enter afterwards showed the results but did not open the first one.
- `GET /api/v1/sales/nearby-points` returned **503** `Sales data is loading` with `Retry-After: 10`. Every parcel click logs this as a console error (see M6).
- **Fix:** report municipality, search and sales health as component status, and define which dependencies are essential to serving the app. Gate overall readiness only on those essential dependencies; a municipality-enrichment outage should be visible as degraded service without making unrelated pages unavailable. Add bounded retries/fallbacks or a short-lived cache for transient municipality failures; profile cold-start latency before adding startup warming.

#### H3. A default OMI quote is presented as the parcel's value
- Parcel `L781B016200.339` (central Verona). The OMI section says "The OMI zone was not detected automatically: check the selection." The dropdown behind it holds **77** zone/type/condition combinations for the whole municipality. It is pre-selected on the first row, `Zone B2 · Negozi · NORMALE · 2025 S1` (a **shop** quote).
- The stat strip above shows that row's figures as the parcel's: **Sale price (OMI) 2,500–5,000 €/m²**. The OMI section also reports a **gross rental yield of 9.6 %** and a **95.8 % sale-price percentile**. See `10-sheet-omi-section.png`.
- That contradicts the notice directly above it, and a user who skims the strip would read a shop price as the land value. The 10-17 audit made the chips say "OMI zone" and "Municipal"; the underlying problem (a guessed zone) remains.
- **Fix:** when the zone is not detected, leave the stat chip at "—", keep the selector on a placeholder and compute no quote until a zone and property type are selected or reliably derived. Label the selected inputs and their source.

### Medium

#### M1. The desktop sheet covers a parcel selected on the right of the map
- At 1440×900 the sheet occupies x 857–1375. Clicking at x = 1000 selected parcel 339, which then sits **under the sheet**. The URL's `lat`/`lng` did not change, so the map did not pan to keep the parcel visible. I could not see a highlight for the selected parcel in any desktop screenshot, either.
- **Fix:** after selecting, pan or `fitBounds` with the sheet's padding (the phone and tablet layouts already treat the sheet as an inset). Make the selection outline more prominent than the other parcel outlines.

#### M2. Language switch discards the view and the selection
- With a parcel open at zoom 18, choosing Italiano navigates to `/map?lang=it&…&lat=41.98&lng=12.55&zoom=6.07`: the Italy overview, parcel closed. See `22-italian-sheet.png`. The 10-17 audit fixed persistence of the language choice, but not preservation of the page state.
- **Fix:** update only the `lang` query parameter while preserving the other query parameters and hash.

#### M3. Ambiguous search results leave stale UI
- After a parcel reference with several polygons was searched, the dropdown showed **two identical suggestions**, with the same label and Polygon ID `495784906341173`. See `08-deeplink-parcel-only.png`. The API returns `409 This reference has multiple parcel polygons. Choose a specific map feature.`; this is an expected selection-required response, but the UI also logs it as an error.
- Clicking a different parcel on the map left the old query text and both stale suggestions in place, over the map. Escape did not close them (`09-normal-parcel.png`).
- **Fix:** deduplicate identical feature IDs, present distinct parcel choices for a 409, and handle that response as a selection state rather than a console error. Clear or collapse the dropdown when the selection changes and on Escape.

#### M4. The sheet is very long
- At 1440×900 the scrolling area is **390 px high for 4,875 px of content**. It holds about 40 collapsible sections. Data coverage reports "5/21" available. Many sections are one-line headings (Terrain, Land cover, Safety, …).
- The first tab, "Value", opens on "Cadastre" (reference, parcel, sheet, municipality, province, region, area) rather than on value. The OMI block, the main reason for the tab, sits below it.
- **Fix:** collapse sections that have no data into a single "Not available for this parcel" list, and open the most useful section first. Group the 21 coverage items.

#### M5. Road parcels are better but still not clean
- `STRADA307` now shows the note "Public road parcel: valuation, auction and solar sections do not apply." Good. It still shows the municipal flood chip **in red** ("High · 7.5%"), a municipal risk score, and the primary **"Purchase cadastral query"** button. See `06-parcel-sheet-desktop.png`.
- **Fix:** visually distinguish municipality-wide flood and risk context from parcel facts (including neutral severity styling), and remove or demote the purchase button for public-domain parcels.

#### M6. Auction section repeats its message and logs an error per click
- "Nearby auction sales are unavailable." appears **three times** in the visible section, plus a Retry button. The 503 above shows up in the console on each parcel click.
- **Fix:** one message and one Retry. Treat "loading" (`Retry-After`) as a state, not an error.

#### M7. Loading and status indicators overlap or contradict
- The "Loading parcel details… 10 s" card sits on top of the shortlist button. At 1024×768 it also covers part of the map attribution (`12-tablet-landscape-1024.png`). The counter was above 10 s in the browser. `parcel/details` took 5.2 s by `curl`.
- The map showed "Map ready" and "Loading map tiles… 2 s" at the same time (`11-layers-panel.png`).
- **Fix:** put transient status in one slot above the attribution, and replace "Map ready" while anything is loading.

#### M8. Dossier PDF took 10 s in one sample
- `GET /api/v1/enrichment/parcel/dossier/L781B016200.339` returned a valid 202 KB PDF in **10.0 s** (3 s on 10-17). Cold start is likely, but I did not repeat the call, so the figure is one sample.
- **Fix:** show a "Preparing PDF…" state while the request runs. Repeat cold and warm timings, then profile the slow path before deciding whether to warm the Typst engine.

#### M9. At 1024×768 the sheet overlaps the search card
- The search card spans x 280–640 and the sheet starts at x 484. The notice text is cut off ("Search fallback sends your place …") and the placeholder is truncated ("Search municipality or parcel re…"). See `12-tablet-landscape-1024.png`.
- **Fix:** collapse the search card to the input row while the sheet is open, or move the sheet's left edge past the card at this width.

#### M10. On a phone the sheet leaves 217 px of map
- At 390×844 the sheet is 627 px high (74 % of the screen). The selected parcel is not visible, and the six tabs sit in a horizontally scrolling strip with a visible scrollbar and "Data" cut off (`14-phone-390.png`).
- **Fix:** start the sheet at a half-height peek and let the user drag it up. Hide the scrollbar and add an edge fade to the tab strip.

#### M11. Many tap targets are smaller than the comfortable target size
- Of 110 visible interactive controls on the map with a parcel open, **105 are under 44 px** in at least one dimension. Treat 44 px as a usability benchmark, not a WCAG AA pass/fail threshold. The section `<summary>` rows are 21 px high and the footer links ("Find adjacent parcels", "SISTER building records", "Open analysis", "Clear selection") are 23 px high, below WCAG 2.2 SC 2.5.8's 24×24 CSS-pixel target threshold. I did not check the spacing exception or other exceptions, so this is a potential conformance issue rather than a confirmed failure ([W3C explanation](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)). The map's own action buttons are 38–44 px.
- **Fix:** raise `summary` and footer link hit areas to at least 32 px (44 px on coarse pointers). For any target under 24×24 px, verify that it meets a WCAG 2.5.8 exception, including the spacing test.

#### M12. Layers panel text is boilerplate
- Every one of the 21 overlays carries a second line such as "Coverage not reported · Source version shown in feature details" or "From zoom 9 · Source date not reported". The line repeats and says nothing, and it doubles the panel length. There is no search or filter. The panel needs scrolling to reach the POI and sales groups (`11-layers-panel.png`).
- **Fix:** show a second line only when it carries information (minimum zoom, partial coverage). Add a filter field above 15 entries.

### Low

- **L1. Dark mode keeps a light basemap.** The shell and the sheet turn dark, the OpenStreetMap basemap stays bright (`15-dark-desktop-sheet.png`). Pair the dark theme with a dark basemap by default.
- **L2. Crawl and sharing basics.** `/robots.txt` and `/sitemap.xml` return 404, `/favicon.ico` redirects (301), and the map page has Open Graph `type`, `title` and `description` but no `og:image` and no canonical link. `/docs`, `/redoc` and `/openapi.json` are public (carried over from 10-17 L6).
- **L3. `/landing` is unreachable from the app.** The logo links to `/`, which redirects to `/map` (307), and the 10-17 rewrite of `/landing` has no inbound link.
- **L4. English basemap labels in the Italian UI.** The dark basemap shows "ITALY, Florence, Naples, Vatican City" under an Italian interface (`22-italian-sheet.png`). Carried over from 10-17 L9. The Italian search placeholder is also truncated ("Cerca un comune o il riferimento della par…").
- **L5. Auth-page assets are unversioned and revalidate.** `/static/css/auth.css` and `/static/auth-register-form.js` are referenced without `?v=` and receive `Cache-Control: no-cache` with ETags; versioned `asset_url()` assets already receive `immutable`. Because the auth page currently fails (H1), the browser did not load these assets through a working login flow. The map page is 215 KB of HTML and 143 requests on load, though compression works (`map-v2.js` 417 KB → 98 KB). Carried over from 10-17 L5.
- **L6. `/map-legacy`** still has a "DEPRECATED" watermark over the map, no `<main>` landmark, a 2.1 s load, and a language selector that shows only a flag.
- **L7. `/map_table`** fails its Bokeh WebSocket (`ws://127.0.0.1:5006/dashboard/ws`, handshake rejected) and logs three console errors. The page degrades to a readable "Interactive table unavailable" message. The page also has no meta description.
- **L8. CSP is permissive.** `script-src` allows `'unsafe-inline'` and `'unsafe-eval'` and lists several CDNs and a hard-coded `127.0.0.1:5006`. The CDN scripts I checked (MapLibre, TopoJSON) carry `integrity=`. This comes from the auth middleware (carried over, 10-17 L3).
- **L9. Intermittent cold starts.** `/privacy` took 6.0 s on its first request in the route sweep and 17 ms when requested again.
- **L10. First-run guide.** The modal opens on every fresh browser profile, over a map that shows no parcels, with "Next" focused. It is correct and dismissible. Consider a persistent "Don't show again" preference plus a way to reopen the guide from Help.

## 4. What worked

- **Performance of the shell:** LCP 208 ms, CLS 0.005, three long tasks of 62–97 ms, JS heap 46 MB. Tiles return in about 3 ms (50 KB). `/health` is 3 ms.
- **Responsive layout:** no horizontal overflow at 1440, 1024, 768 or 390 px. The sheet's scroll area is 217–422 px at the three smaller sizes. The close button is reachable at every size and the sheet itself does not cover the attribution; a separate loading card overlaps it in one 1024 px capture (M7).
- **Accessibility structure:** every visible control has an accessible name, no duplicate IDs, one `<h1>` and a `<h2>` for the sheet, labelled landmarks, live regions for status, a skip link, visible focus rings on every control I tabbed through (22 stops), and tab semantics via `aria-current`.
- **Data labelling:** chips say "Municipal" and "OMI zone", technical identifiers sit under "Technical details", the PVP and OMI notes state what the data is not, and most missing values show "—" rather than zero. H3 is an exception: an OMI quote appears even though its zone is unknown.
- **Failure messages:** the municipality outage, the search outage and the ambiguous reference each show a readable message, not a blank state.
- **Security headers:** HSTS, `X-Frame-Options: DENY`, `nosniff`, a referrer policy and a permissions policy are present.
- **Static pages:** `/landing`, `/data-sources`, the four legal pages and `/notifications` load in 35–280 ms with a title, description and `<h1>`. The 404 page is styled.
- **Italian:** the shell, sheet chrome and map controls are translated.

## 8. Change made during the audit: left sidebar for admin users only

Requested mid-audit: show the theme's left sidebar to admin-role users only.

- **Mechanism:** `aecs4u-theme`'s `base.html` renders the sidebar, its toggle button and the `sidebar-visible` / `sidebar-hidden` body class from the `sidebar_enabled` template variable. Extra render context overrides the theme config, so the flag is passed per request.
- **Code:** [land_registry/main.py](../land_registry/main.py) gains `_sidebar_enabled(user)`, which reuses the existing admin check `is_purchase_admin` (superuser, `has_role("admin")` or an `admin` entry in `roles`). It is passed from five theme-rendered routes: `/map`, `/map/embed`, `/omi/valuation`, `/profile` and `/settings`.
- **Result:** signed-out and non-admin users get `body.sidebar-hidden`, no `#sidebar` and no toggle. The map fills the full width (stage 0–1440 px, no overflow at 390 px). Verified in the browser: `23-no-sidebar-nonadmin.png`.
- **Tests:** [tests/test_sidebar_admin_only.py](../tests/test_sidebar_admin_only.py) covers the flag for no user, a customer, an admin role and a superuser, and the rendered `/map` and `/settings` HTML for each. 16 tests pass together with `tests/test_account_pages.py`.
- **Not verified:** the admin case in a real signed-in browser session (blocked by H1); it is covered by the dependency-override tests only.
- **Side effect addressed:** the themed map's welcome guide now links to **Data sources and reuse**, so the authenticated route remains discoverable when the sidebar is hidden. The link is also present in the fallback map template.
- **Not changed:** `/landing`, `/data-sources`, the legal pages and `/map-legacy` render their own templates. None of them showed a sidebar when checked.

## 10. Implementation follow-up (2026-10-30)

The findings above describe the signed-out application observed on 10-29. This follow-up records code changes and targeted regression checks made after that capture. It is not a full browser re-audit; the original screenshots remain the 10-29 baseline.

| Finding | Follow-up status | Change or remaining evidence |
|---|---|---|
| H1 | **Fixed; local HTTP and browser authentication verified** | Auth templates now select the installed theme's supported parent and missing templates return a controlled 503. Production debug mode is forced off. Both supplied local-account credentials initially returned 401. The password for `demo@aecs4u.com` was reset from the supplied file and the saved hash verified. The same account signed in through the Chromium login form and rendered `/map`, `/profile`, `/settings`, and `/data-sources`; sign-out returned to login. The login and registration pages render in Chromium. `/settings` also requests the Developer API key list, which returns 503 because API-key authentication is not installed; the page has an explicit unavailable message for this condition. |
| H2 | **Readiness gates required parcels; source recovered at 13:12 UTC; auction feed cold-start behavior is intermittent** | The source implementation asks `health()` to check only `cadastral-parcels`, so a slow optional layer cannot consume the readiness budget. A new hard 3-second deadline cancels the health task and returns degraded readiness without waiting for cleanup. Municipality responses are cached for 15 minutes. Lookup exceptions and timeouts are bounded to 8 seconds; a fresh cached profile is returned with `X-Data-Stale` and a warning, or the endpoint returns 503 with `Retry-After: 5`. Current targeted regressions passed for the readiness deadline, request-cancellation cleanup, and municipality stale-cache/timeout behavior. Live observations were inconsistent: `/ready` returned 503 at 08:03 UTC, 200 around 08:04 with 19 layers available, then 503 again at 08:31.
