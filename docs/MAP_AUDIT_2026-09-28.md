# `/map` design, quality and layer audit — 2026-09-28 (Cesena / Romagna coast)

**Target:** `http://localhost:8011/map?lat=44.204628&lng=12.424493&zoom=10.03` (Cesena–Cesenatico–Rimini, zoom 10)
**Branch:** `feature/map-srs-implementation` at `57b6895`, with the uncommitted working tree listed in `git status`. That tree matters: it moves cadastral sheets and parcels from `spatial.cadastral_*` (Veneto only) to the national FDW tables `catasto.fogli` / `catasto.particelle` (`land_registry/map_layers.py`).
**Tooling:** Playwright MCP (Chromium, 1440×900 and 375×812), `curl` against the running API, and MVT decoding with `mapbox-vector-tile` + `shapely` in a throwaway `uv run --no-project --with …` environment.
**Screenshots:** [`docs/map-audit-2026-09-28/`](map-audit-2026-09-28/)
**Previous audit:** [MAP_AUDIT_2026-09-26.md](MAP_AUDIT_2026-09-26.md) (Palermo / Verona). Its IDs are not reused here.

## 1. Summary

At this location the two layers the page exists for — **cadastral parcels and cadastral sheets — are broken**. The geometry is fine; the delivery path fails:

- **Parcels never load.** 0 of every parcel tile requested from z14 to z18 succeeded. Each one returned 503 after 8–13 s, in Cesena and in Verona alike. The attribute table's parcel query returns 500. The layer list still says "Available".
- **Sheets load only intermittently.** At z10–z12 most tiles return 503. At z13–z18 they take 2–11 s, and the same tile flips between 200 and 503 from one request to the next. What does arrive is correct: 69 decoded sheet features had 0 invalid geometries, and they line up with the ISTAT municipal boundary to within 25 m.
- **The client retry loop has no limit** (C2). Each failing source is re-requested about 6 times a second, indefinitely, and tiles that had already loaded are re-downloaded too. That adds load to a server that is already timing out.
- **The dev server died during the audit** (C3). Its last response was a bare `500 Internal Server Error` on a sheet tile. The user restarted it.
- **The user is never told.** The status pill stayed empty through every failure. The "Some map data failed to load" message cannot appear, because of C2.
- **Six catalog layers report "Not available"** (`relation_exists: false`): OMI zones, postal zones, hazard areas, census sections, urban sections and maritime concessions. All six were served on 2026-09-26. Their checkboxes can still be ticked; nothing happens and no message is shown.

These worked well: administrative boundaries, POIs, subsidence (EGMS), municipality profiles, live POI, fires, Civil Protection alerts, Quality of life (BES), search results, theming, and phone-width layout (§5).

> **Remediation (same day):** every finding except C3 (crash cause not captured) and the data gaps behind part of H2 is fixed and browser-verified. Found and fixed during remediation: region-colliding parcel IDs, a whole-table scan on every OMI tile, and seams along every OMI tile edge. See [§9](#9-remediation-log). The map test suites went from 76 passing / 14 failing to 109 passing, and the full suite passes (1,123 tests).

## 2. Scope, method and caveats

1. Loaded the target at 1440×900 (dark, then light) and 375×812. An init script hooked the MapLibre constructor (`window.__auditMap`) so I could read the live style, layer visibility and `queryRenderedFeatures` without changing app code.
2. Switched every overlay on and off at z10, then at Cesena centre (44.1391 N, 12.2431 E) at z13, z14, z15, z16 and z16.5. For each layer I logged every `/api/` response (status and latency) and counted rendered features.
3. Exercised the live layers (POI, fires, Civil Protection, auctions), Quality of life, the subsidence measure switch, map click and popup, attribute table, search and keyboard, and theme toggle.
4. Tested tile endpoints directly with `curl`, one zoom at a time, including a known-good Verona parcel tile for comparison.
5. **Geometry checks on sheets:**
   - Decoded tiles to check validity and buffer bounds.
   - Compared the union of Cesena (`C573`) sheets with the Cesena municipal boundary from `/map/layers/geo-boundaries/features`: area overlap, plus a brute-force best-fit translation over ±300 m.

**Caveats:**

- **No direct database comparison this time.** The permission policy blocked reading the 8011 server's environment, which holds the database connection details, so every data statement here is based on API output.
- **The server crashed partway through** (C3) and was restarted by the user. Checks after that point ran on the fresh process, and every failure pattern reproduced after the restart.
- **Some layers were switched off by the user**, from outside the audit, during the first pass. The resulting "parcels unticked at z16" state is not reported as a defect. Screenshot `04` was renamed to avoid suggesting one.
- Timings are single-run observations on a dev server (`--reload`), not benchmarks.

## 4. Findings

Each finding lists **evidence**, **location**, and a **suggested fix**.

### Critical

#### C1 — Cadastral parcels never load (FDW query exceeds the timeout)

- **Evidence:**
  - With the browser closed and no other load, `cadastral-parcels/{14..18}/…` for Cesena returned **503 in 8.2–13.0 s every time**, e.g. `18/139987/95179` at 12.6 s on two consecutive tries.
  - The Verona tile `16/34768/23461`, served correctly on 2026-09-26, now also returns 503 after 10.9 s.
  - For the same tiles, sheets return 200.
  - `GET /map/layers/cadastral-parcels/features?…&limit=100` (attribute table) returns **500 after 11.3 s**.
  - The response body is always `{"detail":"Canonical PostGIS map layer unavailable"}` with `Retry-After: 2`.
- **Location:**
  - `map_layers.py` `_read_italian_cadastral_mvt`. For parcels it queries the foreign table `catasto.particelle` with
    `WHERE ((t.municipality_code = $a AND t.sheet_number = $b) OR …) AND t.geom_4326 && bounds AND ST_Intersects(…) LIMIT 5000`.
  - Pool limits (`map_layers.py:278-305`): `statement_timeout 8000`, `command_timeout 10`, `pool.acquire(timeout=5)`.
- **Likely cause (to confirm with `EXPLAIN (VERBOSE)` on the Remote SQL):**
  - `postgres_fdw` only ships PostGIS operators when `postgis` is listed in the server's `extensions` option. Without it, `&&` and `ST_Intersects` run locally after fetching every parcel of every candidate sheet, geometry included.
  - A long `OR` chain of `(code AND sheet)` pairs may not be pushed down at all, and the remote table may lack an index on `(municipality_code, sheet_number)`. Either way the remote side scans far more rows than needed, and the query runs past the 8 s timeout.
  - The `LIMIT` has no `ORDER BY`, so a tile that is over the cap drops an arbitrary subset.
- **Impact:** blocks parcel display, click, detail, adjacency, the attribute table, and every parcel-based workflow, everywhere in Italy.
- **Fix, in order of robustness:**
  1. Materialise a local `catasto.particelle` copy, or a slim `(id, municipality_code, sheet_number, refs, geom)` table, with a GiST index. Serve MVT from it the way `spatial.cadastral_parcel` was served before.
  2. Otherwise:
     - Add `postgis` to the foreign server's `extensions` option.
     - Replace the `OR` chain with `JOIN (VALUES …) k(code, sheet) ON …` or `(municipality_code, sheet_number) = ANY($1::record[])`.
     - Make sure the remote table has a composite index.
  3. Keep the timeout, but fail fast with a clear, cacheable "layer degraded" signal (see C2/H4) instead of a 13 s wait.
  4. Add a contract test that times a real parcel tile against a threshold.

#### C2 — The tile-retry loop never stops, and reloads good tiles too

- **Evidence:**
  - With MPS04 switched on at z10, all 9 tiles were requested **every ~1.5 s for as long as the layer stayed on**. That was 144 failing requests in 25 s, about 6 req/s from one layer, and it stopped only when the layer was switched off.
  - Cadastral sheets did the same. Their already-loaded sea tiles (`10/548/370`, `10/548/371`, both 200) were re-downloaded on every cycle, and kept being re-requested after the sheets layer was switched off.
  - The cap message "Some map data failed to load; pan or zoom to retry." never appeared.
- **Location:**
  - `map-v2.js:1648-1668` `scheduleTileRetry` caps retries at 2 through `tileRetry.attempts[id]`.
  - `map-v2.js:3049-3051`: every `sourcedata` event with `sourceDataType === 'content'` resets `tileRetry.attempts[sourceId] = 0`. `source.setTiles()` itself emits that event, so each retry resets its own counter. Any other tile of the same source loading successfully also resets it.
  - `setTiles(tiles)` clears the source's whole tile cache, not just the failed tiles.
- **Impact:**
  - Self-inflicted load on a server that is already timing out (C1, H1). It turns one slow layer into pool starvation for every layer: the 5 s `pool.acquire` 503s, and municipality profiles failing at first.
  - Wasted bandwidth and battery on mobile.
  - It plausibly contributed to C3.
- **Fix:**
  - Reset `attempts` only on `moveend` (already done at `:3075`), never on `sourcedata`.
  - Use exponential backoff with jitter, and read `Retry-After`.
  - Don't retry 4xx responses, or 503s that come back in under 100 ms (deterministic failures like MPS04).
  - Retry only when the layer is visible.
  - Show the status message once the cap is reached.
  - Consider reloading individual tiles rather than calling `setTiles()`, or at least only when every tile in the source has failed.

#### C3 — The dev server process died mid-audit

- **Evidence:**
  - During a z12 sheet sweep, tile `12/2185/1487` returned a **bare `Internal Server Error` (21 bytes, not the JSON 503)**. Every later request got connection-refused, and no `uvicorn` process was left on 8011.
  - No kernel log entry was visible to the audit user.
- **Location:** unknown. The traceback, if any, is in the terminal that ran `run_dev.py`.
- **Likely contributors:**
  - The load from C2 on top of C1/H1.
  - The FDW path's large result sets.
  - The known psycopg2-binary TLS segfault. It was fixed for `map_layers`, but still applies to any code path that uses psycopg2, per the project notes.
- **Fix:**
  - Capture the terminal output of the next crash. If it's a SIGSEGV, run `python -X faulthandler`.
  - Check whether any tile or enrichment path still uses psycopg2 over TLS.
  - Re-test after C2 is fixed.

### High

#### H1 — Cadastral sheets are slow and intermittent (the sheet cache thrashes)

- **Evidence:**
  - At z10, 4 of 5 tiles failed within ~5 s at first, then 6 of 8 on every retry.
  - Isolated `curl` requests:
    - z10: 503 after 8.8 s
    - z11: 503 after 12.3 s
    - z12: 503 after 12.9 s
    - z13: 200 after 10.7 s
    - z14: 503 after 5.0 s, but 200 after 4.3 s and 2.7 s on other attempts
    - z16: 200 after 1.4–6.5 s
  - An all-sea tile (`10/548/371`, 0 bytes) took 2.6 s.
- **Location:** `map_layers.py` `_sheets_for_municipality` and `_read_italian_cadastral_mvt`.
  - Each tile first finds the municipalities it touches, then loads **every sheet geometry of each municipality** from `catasto.fogli` over the FDW.
  - The results go into an LRU cache capped at **12 municipalities** (`map_layers.py:550`).
  - A z10 tile around Cesena touches several dozen municipalities, so neighbouring tiles evict each other's entries and reload them over and over.
  - The second, key-filtered FDW query then runs on top of that.
- **Fix:**
  - Precompute a local sheet index table `(municipality_code, sheet_number, bbox/geom)` with a GiST index, and pick sheets with one indexed `&&` query.
  - Or raise the cache size and key it by tile neighbourhood.
  - Serve z10–z12 from a generalised local table, or raise `min_zoom` to 12.
  - Short-circuit tiles with no municipality early. The sea tile should cost a few milliseconds, not 2.6 s.

#### H2 — Six catalog layers lost their source relations

- **Evidence:**
  - `/map/layers/health` reports `relation_exists: false` (so `Not available`) for:
    - `urban-sections`
    - `market-zones`
    - `postal-zones`
    - `hazard-areas`
    - `census-sections`
    - `maritime-concessions`
  - The same applies to `landscape-constraints` and `heritage-protections`, which don't appear in the panel.
  - The previous audit rendered OMI, postal and hazard layers two days ago.
  - `/map/omi/filters` returns 503.
- **Location:** database or configuration. Either the 8011 server points at a different database than the one used on 09-26, or those relations were dropped or renamed (the working tree changed several `MapLayerSpec` tables).
- **Fix:** confirm which database the 8011 server uses, then fix the catalog table names or restore the relations. Add a startup log line listing unavailable layers.

#### H3 — "Not available" layers can still be switched on, with no feedback

- **Evidence:**
  - Ticking *OMI market zones* leaves it checked, adds no map layer, and shows no status. The OMI controls under it still say "Years load when the layer is switched on."
  - Every unavailable layer also keeps its sub-controls (OMI year/value/type/condition, CAP filter), which makes the panel longer for nothing.
- **Location:** `map-v2.js` `renderLayerCatalog` (`input.disabled` only checks `min_zoom > 22`) and `loadLayerHealth`, which only changes the meta text.
- **Fix:**
  - When `health.available === false`, disable the checkbox and set `aria-disabled`.
  - Collapse the sub-controls.
  - Show "Unavailable on this server", or at least surface the first failure in the status pill.

#### H4 — Failures are never shown to the user

- **Evidence:**
  - Across every failure in this audit, `#mapStatus` stayed empty:
    - parcels (C1)
    - sheets (H1)
    - MPS04 (C2)
    - OMI filters (H2)
    - the attribute table (M2)
  - The layer list keeps saying **"Available"** for parcels while every parcel tile fails.
  - At z16 with no parcels drawn, the only hint in the UI is nothing at all.
- **Location:** `map-v2.js` error handling (`map.on('error')`, `handleLayerFailure`, `loadLayerHealth`).
- **Fix:**
  - Once a layer has had N consecutive failures, mark its row "Temporarily unavailable" and show a status message with a Retry action.
  - Keep health "Available" for "relation exists" only if the label says so. Better, add a tile-latency or success signal to health.

#### H5 — The switch to the national cadastral tables left stale or missing metadata

- **Evidence:**
  - The catalog now declares sheets and parcels `coverage: "full"`, `coverage_note: "Italy"`, with no `coverage_bounds`.
  - But `map-v2.js:1045` still hard-codes "No cadastral parcels published for this area yet (coverage: Veneto)."
  - The new parcel MVT drops `area_sqm` and `source_release`, and emits `national_cadastral_reference` but not the `canonical_reference` that the spec's `properties` list advertises.
  - The detail panel (`map-v2.js:1164-1167`) and the freshness line (`:676`) depend on those fields.
- **Impact:** latent. It can't be observed until C1 is fixed, but parcel detail will then show no area and "Source date not available". Reference-based lookups may also break.
- **Fix:**
  - Build the coverage message from `coverage_note`.
  - Alias `national_cadastral_reference AS canonical_reference`, or update the client.
  - Compute `area_sqm` (`ST_Area(geom::geography)`), or document that it's missing.
  - Emit a release/fingerprint property.
  - Add a contract test that the MVT property names equal `MapLayerSpec.properties`.

## 5. What works well

- **Initial load is fast and clean:** DOM `load` in ~390 ms, no JS errors, and the view is restored exactly from the URL (`12.424493, 44.204628, z10.03`).
- **POI MVT:** 204 features in view at z13, all 10 categories with a colour legend, tiles in ~650 ms.
- **Subsidence (EGMS):** 3,540 cells; switching measure refetches with `?variant=` and restyles; values are plausible for the Cesena subsidence basin.
- **Municipality profiles:** attributes are complete (`istat_code`, `observation_count`, `market_zone_count`) and the layer recovers from first-load 503s.
- **Live layers** respond in 30 ms to 2 s, with counts in the labels:
  - live POI: 142 points
  - Civil Protection: 187 alerts, 6 zones in view
  - fires: 0

## 9. Remediation log

Status after the follow-up session on 2026-09-28. Everything below was verified against the real local databases, in Playwright on a separate test instance (port 8765) and with `curl` on the dev server (port 8011).

### 9.1 Root causes found while fixing

- **Cadastral data path (C1, H1).**
  - In `aecs4u-stats`, `catasto.particelle` / `catasto.fogli` are postgres_fdw tables. They point to views in the local `catasto` database, and each view is a `UNION ALL` of 19 **ogr_fdw FlatGeobuf** tables, one per region (3.3 GB for Emilia-Romagna alone).
  - ogr_fdw pushes only a **plan-time constant bbox on the native EPSG:6706 `geom`** into the file's R-tree:
    - `fid = N` and attribute filters each scan a whole regional file (31 s measured).
    - A bbox passed as a bind parameter also scans the whole file.
  - Sheet and parcel numbers are computed in the view, so the old `(municipality_code, sheet_number) OR …` filter scanned every file on every tile.
  - postgres_fdw has no `extensions 'postgis'` option, so no spatial predicate reached the remote side at all.
- **H2 is mostly a schema move.**
  - `spatial.*` no longer exists in the local `aecs4u-stats`. Urban sections, OMI zones, postal zones and hazard areas are now in **`zornade.*`**, unchanged and GiST-indexed.
  - `census_sections.sections` is empty, `demanio_marittimo.concessions` is absent (only a foreign view `agenziademanio.v_agenziademanio_concessions` exists), and `spatial.protection_area` is absent.
- **M9 (MPS04):** a SQL error, `bounds.extent must appear in the GROUP BY clause`, which the tile route turned into a retryable 503.
- **OMI filters:** three `SELECT DISTINCT` scans over the 10.7 M-row `facts.market_quote_fact` table (no index leads on `period`). Each took about 31 s, beyond the 8 s `statement_timeout`.
- **Disk:** the FGB files and the Postgres data directory share one encrypted spinning HDD, which is 100% full. A cold z14 parcel tile is about 5.6 s; warm, it is about 1 ms.

### 9.3 Found and fixed during remediation

- **OMI tiles scanned the whole quote table.**
  - The default period was `MAX(period) FROM facts.market_quote_fact`, about 30 s per tile.
  - Tiles now use the national latest period from the warmed filter lists, or else the latest among the tile's own zones via the `(market_zone_id, period)` index.
  - Result: 4 ms – 0.8 s per tile.
- **OMI tile-edge seams.**
  - Zones were clipped to the exact tile box, so every tile border was drawn as a purple line ([fix-01](map-audit-2026-09-28/fix-01-omi-z13.png), before).
  - The clip now includes the MVT buffer, and simplification follows the zoom level.
  - Result: 0 of 2,099 outline segments lie on tile edges ([fix-06](map-audit-2026-09-28/fix-06-omi-no-seams.png)).
- **Stale cached tiles.** Successful tiles are cached for an hour, so fixed tiles kept drawing old geometry. The catalog now publishes `tile_version` (`TILE_CACHE_VERSION`), and the client appends it to every tile URL.
- **Cold-disk mitigation.**
  - `warm_catasto_file_indexes()` reads each regional file's header and packed R-tree index into the page cache after a 60 s delay. It runs throttled to about 40 MB/s and only for files readable on the host; opt out with `MAP_CATASTO_INDEX_WARMUP_ENABLED=0`.
  - Effect: a cold Marche z14 tile went from 3.6 s to 0.68 s.
  - Trade-off: the first pass after boot competes with Postgres on the same HDD. Later passes hit the page cache.

### 9.4 Still open / needs a decision

1. **`aecs4u-stats` schema move.** `land_registry/stats_service.py` (enrichment and OMI quotes in the parcel panel) and `datashader_service.py` still query `spatial.*` directly. They were not changed here, pending confirmation that `zornade` is the permanent home.
2. **Durable cadastral storage.** Serving national parcels from FlatGeobuf files on a full HDD works, but cold tiles still take seconds. Better options:
   - a GiST-indexed PostGIS copy (`catasto.particelle` materialised with unique IDs), or
   - moving the FGB files to the NVMe/SSD volume.
3. ~~**OMI period index.**~~ **Done.** [`scripts/sql/omi-period-index.sql`](../scripts/sql/omi-period-index.sql) adds `facts_market_quote_period_dims_idx ON facts.market_quote_fact (period, typology, condition)`. It was built on the local database in 18.7 s (`CONCURRENTLY`).
   - The filter loader checks for the index and reads the three lists with loose index scans: 0.03 s warm and 0.42 s cold, versus 11.7–44 s for the full scan. The lists are identical to the full scan.
   - Without the index the loader keeps the one-pass scan.
   - `MAX(period)` takes 0.4 s cold, down from about 30 s.
   - Apply the same script in every other `aecs4u-stats` deployment. Ideally move it into aecs4u-stats's own migrations.
4. **C3.** Capture the next dev-server crash (faulthandler / terminal output).
5. **Production.** Cloud Run only sets the stats DSN. Without a reachable `catasto` database the map falls back to the FDW path, which is correct but slow. Decide how production should reach the cadastral data.


### 9.5 Market → Sales layer (PVP)

The Sales toggle proxied a separate sales app (`LAND_REGISTRY_SALES_BASE_URL`, default port 8016) that runs neither locally nor on Cloud Run, so it always ended with "Sales feed unavailable". It was also disabled for signed-out users.

It now reads aecs4u-stats **`pvp.v_map_sales`** ([`land_registry/pvp_sales.py`](../land_registry/pvp_sales.py)) and is enabled for everyone:

- **Data:**
  - Geocoded sales inside Italy's bounding box are read once, in about 15 s, and cached in memory. The cache refreshes hourly and keeps the last good copy if a refresh fails. The warm-up runs 30 s after startup; opt out with `MAP_SALES_WARMUP_ENABLED=0`.
  - Placeholder geocodes such as `(1, 1)` and `(683, 684)` are dropped.
  - Sales that share an exact coordinate with 19+ others are marked as approximate.
- **Categories:** the 77 free-text property types are grouped into 9 categories. Most upcoming sales have no type, so their notice text is classified with the same keywords, which cut untyped upcoming sales from 2,112 to 233.
- **Panel:** auction-date period (upcoming by default, last 12 months, last 5 years, all), property type with counts, max base price, colour legend, "Show all". The saleability controls were removed because `pvp` has no such scores. The administrative-layer controls show only when `LAND_REGISTRY_SALES_GEO_LAYERS_URL` is configured.
- **Popup:** loaded on click from `/api/v1/sales/points/{id}`: type, auction date, base price, address, listing place, description, and a listing link when the URL is absolute.
- **Also fixed:**
  - Clicking a sale no longer selects the parcel underneath.
  - Sales layers take part in the overlay order (the list named a non-existent `point-sales-properties`).
  - Cluster counts render now; the label layer had no self-hosted font, so every glyph request returned 404.
  - Click handlers are bound once instead of on every refresh.
