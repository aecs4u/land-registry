## 1. Summary

This audit records the **pre-remediation baseline** observed on 2026-09-26. For the layers and tiles that loaded successfully, rendered feature IDs matched the aecs4u-stats database for administrative boundaries, OMI zones, postal zones, and Veneto parcels. Failed tiles caused missing features, so this does not mean the full viewport was always represented faithfully.

The main problems at baseline were:

- **Parcel selection is unreliable.** The reference lookup behind every parcel click does a full scan of 4.68 M rows. It times out whenever the row isn't near the start of the heap.
- **Three features are broken in the UI but look enabled:**
  - In dark mode, popup text is effectively invisible (about 1.04:1 contrast).
  - The attribute table renders underneath the map canvas.
  - The live POI layer always returns zero results with the default category selection.
- **Municipality search only matches exact names**, because SQL parameters are bound in the wrong order. It then falls back to public Nominatim as you type, which that service's usage policy forbids.
- **The requested location has no cadastral data at all.** aecs4u-stats only has Veneto parcels. The page never says so, and keeps prompting "Zoom in to see cadastral parcels".
- **Tiles that fail on a cold cache are never retried.** They leave silent holes: 17 of 238 hazard polygons were missing in the audited view.

> **Remediation:** this file records both the pre-remediation baseline and the follow-up implementation. See [§8](#8-remediation-log) for current status. H6 was revised after re-checking showed that the apparent self-neighbour was a different polygon with the same reference.

The severity counts below describe the **baseline**, not the remaining backlog. The 2026-09-26 run below is historical; the latest follow-up on 2026-09-27 is recorded at the end of §8.1.

- **Fixed and browser-verified:** C1–C4, H1, H3–H8, M1–M12, L1–L6, L8–L10.
- **Fixed in the sibling `aecs4u-theme` checkout and browser-checked:** L2 (Google Fonts stylesheet loading).
- **Follow-up checks:** mobile sidebar accessibility state and parcel/Layers stacking now pass at 375 px; parcel/Layers stacking also passes at 1440 px. H2 tile retries recover failed tiles, and the background warmer pauses when live tile queries are active.
- **Regressions from the remediation, found and fixed during review and verification:** municipality names dropped (H1), Civil Protection bulletin empty (M12), idle render loop overwriting every status message (M9, L10), table pagination hidden (M1), and search returning 503 while tiles loaded (H1, M2, M3). See §8.1.
- **Tests:** 52 focused contract tests pass. Latest browser run: 46 checks passed, 3 failed (§8.1).

## 2. Scope and method

1. Loaded the target URL at 1440×900 in both themes, then at 768 px and 375×812. Captured the accessibility tree, console, network, and performance entries.
2. Hooked the MapLibre constructor with an init script (`window.__auditMap`) to read the live style, layer order, paint properties and rendered features (`queryRenderedFeatures`) without changing app code.
3. **Data fidelity:** for each overlay, I compared the set of rendered feature IDs in the exact viewport bounds against `ST_Intersects(geom, viewport)` in aecs4u-stats. I did this at Palermo (the target) and at Verona z16/z17, because parcel coverage only exists in Veneto.
4. Exercised every control: search, layers, the live layers (POI, fires, bulletin, sales, auctions), parcel click/detail/adjacent/copy/save/clear, attribute table, locate, share, Google Maps/Street View, theme toggle, keyboard navigation, and URL edge cases.
5. Traced each defect to source and confirmed root causes with `EXPLAIN ANALYZE` or direct API calls where possible.

The source state was the uncommitted `feature/map-srs-implementation` work tree named above. The exact commit SHA, Chromium version, and database snapshot identifier were not recorded, which limits exact reproduction of timing and rendering results. Timings below are observations from this run, not benchmark guarantees.

> **Note:** during the session the shared browser window was resized to 768×415 and reloaded from outside the audit. I restored the viewport before the desktop checks, and I report the 768 px observations as tablet findings.

## 4. Findings

Each finding lists **evidence**, **location** and a **suggested fix**.

### Critical

#### C1 — Parcel selection times out for most parcels (missing index)

- **Evidence:**
  - Clicking parcel `L781A012400.147` left the status on "Loading parcel…" for about 10 s. Then `/api/v1/enrichment/parcel/by-reference/L781A012400.147` returned **503** and the detail panel never opened ([08](map-audit-2026-09-26/08-parcel-click-result.png) shows the successful case, for contrast).
  - `EXPLAIN ANALYZE` of the lookup ran a **Seq Scan over 4,683,749 rows in 71.6 s**. The pool's `statement_timeout` is 8 s (`map_layers.py:177`).
  - A different parcel (`L781B016200.STRADA300`) resolved in under 1 s only because its row sits early in the heap. Behaviour depends on where the row happens to live.
- **Location:**
  - `map_layers.py:411` (`WHERE national_cadastral_reference = %s OR canonical_reference = %s`).
  - The same predicate appears in `read_adjacent_features` (`map_layers.py:~447`).
  - `spatial.cadastral_parcel` only has indexes on `pkey`, `geom`, `inspire_localid`, `municipality`, `release` and `source_key`.
- **Impact:**
  - Affects parcel click, `?parcel=` deep links, attribute-table row click, "Find adjacent parcels" and exact-reference search.
  - Any arbitrary string in `?parcel=` or `/by-reference/{x}` costs the server a full 8 s scan, which is a cheap load-amplification vector.
- **Fix:**
  - In aecs4u-stats, add `CREATE INDEX … ON spatial.cadastral_parcel (canonical_reference)` and `… (national_cadastral_reference)`, or rewrite the query as `UNION ALL` of two indexed lookups.
  - Client side: a click already has the feature `id` from the vector tile, so fetch `/api/v1/map/layers/cadastral-parcels/features/{id}` (≈1 s, PK lookup) instead of re-resolving by reference. *(Implemented differently: an `?id=` hint on `/parcel/by-reference`; see §8.)*

#### C2 — Map popups are unreadable in dark theme

- **Evidence:**
  - Clicking the map in dark mode opens a popup whose text is `rgb(248,250,252)` on a white `.maplibregl-popup-content`. That is a contrast ratio of **≈1.04:1**.
  - The close button is white on white as well ([03](map-audit-2026-09-26/03-click-z12.png)).
- **Location:** every `new maplibregl.Popup` in `map-v2.js` (e.g. `:746`, `:1156`, `:1252`, `:1468`, `:1521`, `:1638`). Popup content inherits `--color-text-primary` from `[data-bs-theme=dark]`, but MapLibre's own stylesheet keeps the white background.
- **Fix:** theme the popup in `map-v2.css`:
  - `.maplibregl-popup-content { background: var(--direct-map-panel); color: var(--direct-map-text); }`
  - Matching `.maplibregl-popup-tip` border colours per anchor.
  - `.maplibregl-popup-close-button { color: var(--direct-map-muted); }`
  - `.map-popup-label` hard-codes `#64748b`; use the muted token instead.

#### C3 — The attribute table renders underneath the map and cannot be closed by mouse

- **Evidence:**
  - After clicking "Attribute table" the toggle shows as active, but nothing appears ([18](map-audit-2026-09-26/18-attribute-table.png)).
  - The card's computed `position` is `static`, and `elementFromPoint` over the card returns `maplibregl-canvas`.
  - Playwright could not click `#mapTableCloseButton` because `#locateButton` intercepts the pointer.
- **Location:** `map-v2.css:28`. The shared `position: absolute; z-index: 2` rule lists every floating card **except `.map-table-card`**, so its `left/right/bottom` offsets (`:94`) do nothing.
- **Fix:** add `.map-table-card` to the selector at `:28` (with `z-index: 3`), and add Escape-to-close. Escape currently does not close it.

#### C4 — Live "Points of Interest" layer is always empty with the default categories

- **Evidence:**
  - With all ten categories selected (the default), `GET /api/v1/enrichment/pois/?…&categories=universities,schools,…` returns `total: 0`.
  - The same request with no `categories` returns **25**, and `categories=supermarkets` returns 8.
  - Any comma-separated pair returns 0. Repeated params (`categories=schools&categories=supermarkets`) return 13.
- **Location:**
  - `routers/enrichment.py:116` declares `categories: Optional[List[str]]` (repeated query params).
  - `map-v2.js:1306` sends `categories.join(',')`, which arrives as one unknown code `"a,b,…"`, so `c.code IN ('a,b,…')` matches nothing.
  - `poi-report` and the explorer use `_poi_category_query()` (`enrichment.py:133`), which *does* split on commas. The three endpoints disagree.
- **Fix:** make `/pois/` accept the same comma form via `_poi_category_query`, or send `params.append('categories', c)` per category. Add a contract test.

### High

#### H1 — Municipality search only matches exact names (SQL parameters bound in the wrong order)

- **Evidence:**
  - `?query=Palermo` finds Palermo.
  - `?query=Palerm`, `alermo`, `Monte` and `San ` all return **0** canonical results.
  - Only ISTAT-code prefixes do partial matching (`820` → 20 municipalities).
- **Location:** `map_layers.py:573`. The SQL is `canonical_name ILIKE $1 OR istat_code ILIKE $2 ORDER BY lower(name)=lower($3), lower(name) LIKE lower($4)`, but it is called with `(normalized, prefix, pattern, pattern)`. So `$1` has no wildcards, and the ORDER BY compares against `%…%`.
- **Fix:** bind `(pattern, prefix, normalized, prefix, limit)`. Add a regression test for partial names.

#### H2 — Failed tiles leave permanent, silent data holes

- **Evidence:**
  - On first load, hazard tiles `12/2200/1579`, `12/2199/1578` and `12/2199/1579` returned **503** because the cold query exceeded the timeout. Re-requested moments later, `12/2199/1579` served 9.1 KB in 7 ms (the other two were not re-measured).
  - MapLibre does not retry failed tiles. All 17 missing hazard polygons lie in `12/2199/1579`. (The one POI not found in §3.1 is unrelated: its tile loaded normally.)
  - The status pill kept saying "Map ready".
  - `/api/v1/map/metrics` over the session: **76 of 364 vector tiles took >1 s, 39 took 3–10 s, 5 errored**. Examples: `market-zones z13` 7.3 s, `cadastral-parcels z15` 5.0 s, `urban-sections z13` 2.5 s. `layer_health` hit its 5 s client abort on first load.
- **Location:** `routers/api.py:~4462-4467` (503 on any exception), `map_layers.py:291-326`.
- **Fix:**
  - Warm or pre-generate low-zoom tiles for national layers.
  - Return retryable failures with `Retry-After` and add a `map.on('error')` handler that reloads the source tile once and surfaces "Some tiles failed to load — Retry" in the status pill.
  - Make sure error responses are never cached (the success path sends `max-age=3600`).

#### H3 — The requested area has no cadastral data, and the UI never says so

- **Evidence:**
  - At the audited URL the DB has **0 parcels / 0 sheets / 0 urban sections**, because parcel coverage is Veneto only (§3.3).
  - The page shows "Zoom in to see cadastral parcels" ([01](map-audit-2026-09-26/01-desktop-initial.png)), and the layer list marks "Cadastral parcels" as **Available**.
  - The only hint is the generic "Some layers have partial regional coverage." A user who zooms in finds an empty map.
- **Fix:**
  - Publish a coverage extent (or per-region flag) in the layer catalog/health.
  - When the viewport is outside it, replace the help note with "No cadastral parcels published for this area yet (coverage: Veneto)".
  - "Available" in the layer list currently means "the relation exists". Rename it or drop it.

#### H4 — Parcel detail shows raw IDs and empty key values

- **Evidence:**
  - The panel subtitle and the *Municipality* row show `11180`, not "Verona".
  - *Area* shows "—" because `area_sqm` is NULL for every Verona parcel.
  - *National reference* is NULL throughout, so the national-format workflows (search, adjacency self-exclusion, enrichment) degrade.
- **Location:** `map-v2.js:~561` (`renderParcelPanel`); the gap is in aecs4u-stats `spatial.cadastral_parcel`.
- **Fix:**
  - Join `geo.geo_unit.canonical_name` in `read_feature_by_reference` / `read_feature_details`.
  - Fall back to `ST_Area(geom::geography)` when `area_sqm` is NULL, labelled "computed".
  - Backfill `area_sqm` and `national_cadastral_reference` in the Veneto load.

#### H5 — "Loading optional enrichment…" never resolves

- **Evidence:** `/api/v1/enrichment/parcel/details/L781B016200.STRADA300` returns 404 ("No enrichment data found"). The panel keeps the loading text indefinitely.
- **Location:** `map-v2.js:850`, where `if (!response.ok) return;` leaves the placeholder in place.
- **Fix:** on a non-OK response, render "No enrichment available for this parcel" (404) or "Enrichment unavailable — retry" (5xx).

#### H6 — Parcel references are not unique, so reference-based selection is ambiguous *(revised during remediation)*

- **Evidence:**
  - `canonical_reference` is not unique in `spatial.cadastral_parcel`. Verona has 106,788 rows but only 102,453 distinct references. Road and water pseudo-parcels are split across many polygons; `L781B016200.STRADA300` alone is 10 rows.
  - Every by-reference lookup ends in `LIMIT 1` with no `ORDER BY`, so it returns an **arbitrary** polygon. A click on one piece of a road could highlight and fly to another piece.
  - The audit first reported that "Find adjacent parcels" listed the selected parcel itself. On re-check, the listed `STRADA300` was a different polygon with the same reference, i.e. a genuine neighbour.
  - Separately, the old self-exclusion (`national_cadastral_reference IS DISTINCT FROM ref`) could never exclude anything for Veneto, where that column is always NULL.
- **Location:** `map_layers.py` (`read_feature_by_reference`, `read_adjacent_features`).
- **Fix (partly applied, see §8):**
  - Clicks carry the tile feature's primary key, and both lookups resolve the target by `id`.
  - Adjacency excludes the target by `id`.
  - **Still open:** reference-only entry points (deep links, search) remain ambiguous for duplicated references. Deep links should carry the `id`.

#### H7 — Administrative-boundary interaction reports the wrong unit, without a name

- **Evidence:**
  - All four hierarchy levels (ripartizione *Isole*, region *Sicilia*, province *Palermo*, 9 municipalities) are drawn in one layer with no filter.
  - A click in the city reported **province id 107 / geo_unit 8135**, with no name and no unit type.
  - Stacked fills accumulate (4 × 0.075 opacity), so the land tint is uneven by hierarchy depth.
- **Location:** `geo-boundaries` spec (`map_layers.py`, properties `id, geo_unit_id, generalization, source_release`). `generalization` is NULL in the DB.
- **Fix:**
  - Add `unit_type` and `canonical_name` (via `geo.geo_unit`) to the tile properties.
  - Filter or style by level per zoom (for example region <z8, province z8–10, municipality ≥z10).
  - Show the name in popups and resolve clicks to the most specific unit.

#### H8 — Search-as-you-type sends queries to public Nominatim

- **Evidence:**
  - Each debounced keystroke query also goes to `https://nominatim.openstreetmap.org/search?…&q=<text>`, including parcel references (`L781B016200.14`).
  - The results are labelled **"Municipality"** even for streets ("Via Zara 12/14 … Brescia", "Scolo Veron …") ([11](map-audit-2026-09-26/11-search-results.png)).
- **Location:** `map-v2.js:928`, `:882`.
- **Why it matters:**
  - The OSMF Nominatim usage policy forbids autocomplete and requires an identifying UA/Referer.
  - Typed queries leave the platform.
  - Mislabelling confuses users.
- **Fix:**
  - Only call a geocoder on explicit submit, or use a self-hosted or commercial geocoder.
  - Never forward strings that look like parcel references.
  - Label results by OSM `type`/`addresstype`.

## 5. What works well

- **Data fidelity on successful tile loads:** rendered IDs match aecs4u-stats exactly for the compared layers (§3.1). Attributes pass through unmodified, and SRIDs are consistent (4326 everywhere checked). Failed tiles caused the documented omissions.
- **Fast shell:** TTFB 12 ms, FCP 448 ms, DOMContentLoaded 546 ms, HTML 6 KB, 434 DOM nodes.
- **Tile transport:** gzip (~2.2× on parcel tiles), `Cache-Control: public, max-age=3600`, `Vary: Accept-Encoding`. Invalid coordinates return 400 and unknown layers 404. No per-tile truncation in dense Verona at z14.
- **Security headers:** HSTS, CSP, `X-Frame-Options: DENY`, `nosniff`, COOP/CORP. A `?parcel=<img onerror>` payload was not executed.
- **Parcel labels** render with self-hosted Noto glyphs (no third-party font host), and hide below z17.
- **Accessibility basics:** skip link, a single `h1`, `aria-live` status and search regions, labelled icon buttons, keyboard pan/zoom on the canvas, visible focus rings on all tabbable controls.
- **URL state:** view and selection are serialized to the URL, zoom is clamped to 22, and non-numeric coordinates fall back to the national view.
- **Adjacency** returns sensible neighbours; note that duplicated references mean a road can list its own other segments (H6). Copy-link works, and the Civil Protection bulletin (187 zones) and auction layer (6) load.

1. **Municipality names (H1).** The H7 change made `_source_columns` drop `canonical_name` from every layer, so search results and profile tiles showed ISTAT codes. It is now stripped only for `geo-boundaries`.
2. **Civil Protection bulletin (M12).** The L1 script cleanup also removed the TopoJSON parser from `/map`, so the bulletin drew 0 zones and showed “(0)”. The script is restored, and a missing parser now reports an error instead of looking like “no alerts”.

5. **Parcel search plan (M3, C1).** Even with the new indexes, `spatial.cadastral_parcel` had never been analyzed, so the planner walked the primary key (a full scan) and the 2 s search timeout returned 503. The fix was `ANALYZE` (now part of `scripts/sql/map-reference-indexes.sql`) plus a `UNION` of two indexed lookups.
6. **Search under load (H1, M2, M3).** Municipality and parcel search shared the 8-connection pool with tile rendering, so while tiles loaded they waited for a connection and hit their timeouts (503). Municipality search was first moved to a reserved 2-connection pool, which was created lazily and still timed out on the first query. Parcel search now uses the same reserved pool (`routers/api.py`), and the pool is opened in the background at startup (`warm_map_search_source`).

**Database changes applied to aecs4u-stats:** `cadastral_parcel_canonical_reference_idx`, `cadastral_parcel_national_reference_idx`, and `ANALYZE spatial.cadastral_parcel`.
